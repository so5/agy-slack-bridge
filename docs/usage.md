# 使い方と動作リファレンス

セットアップは [install.md](install.md) と [slack-app.md](slack-app.md) に、
許可の保存場所は [permissions.md](permissions.md) にあります。

## できること

- 設定した Slack チャンネルは、それぞれ 1 つの `agy` プロジェクトに 1:1 で対応します。
- 新しいトップレベルのメッセージは、**ボットを @メンションしている**場合に限り、
  新しい `agy` の会話を始めます。このため、チャンネル内のほかの投稿(バッチジョブが
  Incoming Webhook で結果を投稿する場合や、普通の雑談)はプロンプトとして扱われません。
  メンションは取り除かれ、残りのテキストが `agy` に送られます。返信は、そのメッセージの
  スレッドに投稿されます。
- そのスレッド内で返信すると、同じ `agy` の会話が続きます(スレッドのルートのタイム
  スタンプで会話を引き当てます)。**スレッドへの返信にはメンションが不要**で、メンションが
  必要なのは新しく始めるときだけです。ただし、そのスレッドが実際に *有効化* されている
  (保存済みの会話がある、つまりスレッド内のどれかのメッセージがすでにメンションの
  ゲートを通っている)場合に限ります。Slack では、元の投稿者(ボットでも人間でも)に
  応答があったかどうかに関係なく、*どの* メッセージにもスレッドで返信できます。そのため
  「返信かどうか」だけでゲートにすると、誰もメンションしていないメッセージへの返信が、
  いつの間にか会話を始めてしまいます。これはテストで確認済みで、「メンションして初めて
  有効になる」ことを前提とするアプリでは実際に使いにくくなります。
  そこで、有効化されていないスレッドへの返信にも、新しいトップレベルのメッセージと同じく
  メンションが必要です(メンションが必須で、あとで取り除かれます)。スレッド内の
  *どれか* のメッセージがこのゲートを通ったあとは、それ以降の返信はこれまでどおり
  メンション不要です。(後述の `resume <id>: ...` も同様で、新しいトップレベルの
  メッセージだけでなく、有効化されていないスレッドへの返信でも同じように動作します。)
  - メッセージを **編集** して、元になかったメンションを足しても動作しません。理由は
    独立した 2 つあります。(1) テストで確認したとおり、Slack 自体が @メンションを通知の
    対象として評価するのはメッセージを最初に送信した時点だけで、あとからの編集では
    評価しません(*人間* をこの方法でメンションする場合も同じで、ドキュメント化されて
    いませんが知られている Slack の挙動です)。(2) ブリッジが、編集されたメッセージを
    すべて明示的に無視します(編集があると `subtype` が `"message_changed"` になり、
    `subtype` が `None` でなければハンドラーはすぐに戻ります。もともとは Incoming
    Webhook のボット投稿を無視するために入れたものですが、編集も同じように拾います)。
    編集する代わりに、新しいメッセージを送るか、無視されたメッセージに **メンション付きで**
    返信してください。
- 新しいトップレベルのメッセージは、新規の会話を始める代わりに、*既存の* 会話へ接続する
  こともできます。[Antigravity の Web UI](https://antigravity.google.com) で始めた
  会話を Slack から続けたいときに便利です。メッセージの先頭に @メンション(新しい
  トップレベルのメッセージには必須です。上記参照)を置き、続けて
  `resume <conversation-id>` を書きます。

  ```
  @your-bot resume db68d299-5a1c-475a-a1ed-09604f5537e4: 続きをお願い
  ```

  できあがった Slack スレッドは、その会話 ID に接続されます。以降のスレッド内の返信は
  通常どおりその会話を続けるので、最初のメッセージ以降は `resume` を繰り返す必要は
  ありません。

  **注意(テストで確認済み)**: これが [Antigravity の Web UI](https://antigravity.google.com)
  から見えるかどうかは、会話を *どこで始めたか* によって変わります。

  - `agy -p` で始めた会話(このブリッジが作ったものを含む)は、双方向で完全に同期した
    ままです。Web UI からは、`.../r/<your-instance-id>/?p=c%2F<conversation-id>%3Fsection%3D<project-id>`
    という形式の URL で直接開けます(`<your-instance-id>` は、Web UI がすでに提示している
    会話 URL のどれかから正確な値を取ってください)。この方法で開くとサイドバーに
    表示されます(それまでは自然には表示されません)。以後、Web UI から送ったメッセージは
    あとの `agy -p --conversation` の呼び出しから見え(確認: 「Web UI から今送ったのは
    何?」と尋ねたところ、メッセージとタイムスタンプを正しく引用しました)、逆も同様です。
  - Web UI で *対話的に* 始めた会話は、`agy -p` から実質的に拡張することはできません。
    `agy` は同じ `conversation_id` を返し、会話のトランスクリプトログ
    (`~/.gemini/antigravity-cli/brain/<id>/.system_generated/logs/`)にも追記します。
    そのため、こうした会話への `resume` は実際の履歴を読み、文脈に沿った正しい答えを
    返します。しかし、上記の直接 URL を使っても、新しい内容は Web UI にまったく
    表示されません。つまり読み取りだけで、agy はその会話の過去の内容を見て考えることは
    できても、Web UI が表示する側には書き込めません。(Web UI が何を元に描画しているのか、
    正確な仕組みはわかっていません。単純に `.system_generated/steps/` のトレースでは
    ありません。どちらの起源の会話でも、通常の会話のターンにはそのトレースが付かない
    ことがあるためです。)

  実際には、Slack と Web UI の **どちらからでも** 続けられる会話にしたいなら、Slack
  (または `agy -p` を呼ぶほかの手段)から始めてください。Web UI で始めた会話は
  `resume` で Slack から *読む* ことはできますが、Slack 側での続きは Web UI には
  反映されません。
- `agy` の応答に含まれる Markdown(太字、リンク、表、見出しなど)は、投稿の前に Slack
  独自の `mrkdwn` 方言に変換されます。Slack は標準の Markdown をそのままでは描画しない
  ためです(たとえば、表の構文がなく、`**bold**` / `*italic*` ではなく
  `*bold*` / `_italic_` を使います)。
- `agy` が作業している間、スレッドには何も表示されない状態にならず、Slack ネイティブの
  「is thinking...」ステータス表示(`assistant.threads.setStatus`)が表示されます。実際の
  タスクは何分もかかることがあるので便利です。`chat:write` 以外の Slack スコープは
  不要です。ステータスは定期的に更新され(Slack は約 2 分間何もないと自動で消します)、
  返信が投稿されると自動で消えます。
- すべて Slack の **Socket Mode**(手元のマシンから Slack への外向きの websocket)で
  動きます。受信用のポート、リバースプロキシ、公開 URL は不要です。
- メッセージに**添付したファイル**は、プロジェクトのワークスペースの `inbox/<スレッドのタイムスタンプ>/`
  にダウンロードされ、プロンプトで agy に相対パスが伝えられるので、agy は通常のワークスペースの
  ファイルとして読めます（`files:read` スコープが必要）。1 メッセージにつき 5 件まで、1 件 20 MB までです。
  上限を超えたものは取り込まれず、スレッドに、大きいファイルや多数のファイルは Google Drive に置いて
  共有 URL を貼るよう案内する通知が付きます。取得するのは `files.slack.com` の URL だけで、ボットの
  トークンで取得します。ファイル名はベース名に縮めるので、添付が inbox ディレクトリの外に出ることは
  ありません。
- agy の応答が、生成したもの(グラフ、レポートなど)への `file://` リンクに言及して
  いても、Slack ではそのリンクは使えません。ローカルのファイルシステムのパスは、
  誰にも開けないためです。そこでブリッジは、ファイル自体も同じスレッドへの返信として
  アップロードします(`files_upload_v2`、`files:write` スコープが必要)。対象は、認識
  される種類(画像 / PDF / CSV など。`UPLOADABLE_EXTS` を参照)で、かつその agy
  プロジェクト自身のワークスペースディレクトリ、またはその会話自身の
  `~/.gemini/antigravity-cli/brain/<id>/` のアーティファクトディレクトリの下にある
  ものです。「agy がたまたま言及した任意の絶対パス」は意図的に対象外にしています。
  応答が、マシン上のほかの任意のファイルを持ち出す手段になるのを避けるためです。
  1 回の返信につき、20MB、5 ファイルが上限です。
- agy がコード以外の言語タグ(` ```markdown `、` ```text `、またはタグなし)を付けた
  フェンスブロックは、実際にはコードではありません。Slack の mrkdwn のコードブロックは
  もともと言語タグに対応していないため、以前はブロックの先頭に「markdown」や「text」と
  いう行がそのまま表示されていました。この種のフェンスは完全に展開されるので、中の
  見出し / 太字 / リンク / 表は通常どおり描画されます。実在する言語(python、bash など)の
  タグが付いたフェンスは、等幅のブロックのまま、役に立たなくなったタグだけが外されます。
- ` ```mermaid ` ブロックは PNG に描画され、ファイルとしてアップロードされます。Slack
  では誰も読めない図の構文がフェンスで長々と並ぶことはありません。下の「Mermaid
  diagrams」を参照してください。
- 返信に `run_command` の拒否が含まれている場合(下の「Tool permissions」を参照)、
  メッセージには文字の警告だけでなく 2 つのボタンが付きます。**許可して再実行**(その
  コマンドそのものを、この会話に限って許可し、同じプロンプトを再試行し、再試行が終わると
  再び取り消す)と、**拒否** です。これにより、許可の拒否に対して、SSH でログインして
  許可リストを手で編集しなくても、スマートフォンからそのまま対処できます。恒久的な
  許可は意図的に別の手順です(下の「Managing permissions from Slack」を参照)。
  ボタンのクリックにしないのは、コマンド文字列に結びついたボタンだと、クリック時点の
  内容だけでなく、そのコマンドの対象ファイルの *あとからの* 内容まで、知らないうちに
  許可してしまうからです。

これは意図的に、`agy -p ... --output-format stream-json` の薄いプロセスラッパーに
とどめており、agy がすることを再実装するものではありません。Slack のメッセージを
中に流し、`agy` の最終結果を外に返し、Slack のスレッドと `agy` の会話 ID との小さな
ローカルの対応表を保持するだけです。

## チャンネルごとの設定(`config.yaml`)

`tools/setup_agy_project.py` がこれらを書き込みます。`~/.config/agy-slack-bridge/config.yaml`
を手で編集することもできます(`config.example.yaml` を参照)。変更したらブリッジを
再起動してください。

- `project`: このチャンネルが対応する agy のプロジェクト ID(1 チャンネル = 1 プロジェクト)。
- `display_name` / `icon_emoji`(または `icon_url`): チャンネルごとに別の名前とアバターで
  投稿します。`chat:write.customize` スコープが必要です(マニフェストに含まれています)。
- `model` / `effort`: そのまま agy の `--model` / `--effort` として渡されます(選択肢は
  `agy models` で一覧できます)。モデル名の中には、`-high` / `-low` のサフィックスで
  推論の段階をすでに含んでいるものがあり、両方を設定すると `effort` と競合します。
  チャンネルを agy 組み込みの `default-cli-project`(ワークスペースなし)と、
  `gemini-3.1-pro-high` のような高推論のモデルに向けると、リポジトリに結びつかず
  ファイルやツールにアクセスしない、通常の思考モードのチャットチャンネルになります。
- `watched_config_files`: ドリフトから保護するファイル。下の「Config drift detection」を参照。
- `telemetry`: オプトインの利用統計。下の「Usage statistics」を参照。

## Tool permissions

**ツールの権限(Tool permissions)**: ヘッドレスの `agy -p` 呼び出しには、ツールの
権限プロンプトで「承認」をクリックする人間がいません。そのためこのブリッジは、
`--dangerously-skip-permissions` ではなく `--mode accept-edits` で動かします。テストでは、
`accept-edits` はファイルの編集と安全な読み取り専用のシェルコマンド(たとえば `ls`)を
自動で承認しますが、agy が破壊的と判断するコマンド(たとえば `rm`)は、許可エントリに
一致しない限り、引き続き拒否されます。許可エントリは、`~/.gemini/config/projects/<project-id>.json`
にあるプロジェクト自身の `permissionGrants.allow`(下の「Managing permissions from
Slack」を参照)か、agy のマシン全体の `~/.gemini/antigravity-cli/settings.json` の
`permissions.allow`(すべての `agy` プロジェクトで共有。ブリッジは決してここへは
書き込みません)のどちらかです。

一致の判定は、文字列全体の完全一致では **ありません**。また、バイナリ名だけでの許可でも
**ありません**。テストで確認したとおり、*トークン単位で完結した前方一致* です。
`command(git diff)` は `git diff --stat` や `git diff HEAD~1` など、あとに何が続いても
一致します。すでに入力されている各トークン(`git`、`diff`)が完結していて、その後ろが
トークンの境界だからです。`git diffX`(トークンの境界ではない)や `git status`(2 番目の
トークンが違う)には一致 **しません**。エントリ末尾の `*` は、確実には効き **ません**。
テストでは挙動が一定しなかったので、使わないでください。許可リストは狭く育ててください。
`command(aws lambda)` や `command(git diff)` のようにサブコマンドまで含めた前方一致なら
問題なく、たいていそれが有用な粒度です。ただし、`command(rm)` や `command(git)` のような
コマンド名だけの許可は、趣旨を台無しにするので絶対にやめてください。agy がこの理由で
黙ってアクションをスキップすると、実行結果は `status: SUCCESS` で、一見空に見える応答と
`denied_actions` フィールドが返ります。ブリッジはこれを検出し、拒否されたアクションを
示す `:warning:` の注記を Slack の返信に追加します。空に見える応答を眺めることには
なりません。

**複合コマンド(`&&` など)**: テストで確認したところ、agy は複合コマンド行を `&&` の
ようなシェル演算子で分割し、**各サブコマンドを個別に** `permissions.allow` と照合
します。行全体での文字列一致ではなく、「`&&` があれば一律に拒否」という規則でも
ありません。`sleep 10 && aws logs ...` が拒否されるのは、`sleep 10 ...` 単体が許可
リストにないからだけです(後半は `command(aws logs)` に一致します)。`command(sleep)`
も許可すれば、行全体が通ります。逆に、許可されたアクションに許可されていない
アクションを連結しても、すり抜けられません。`command(echo hi)` だけを許可している
場合、`echo hi && touch /tmp/whatever` は、`touch ...` が単体ではどれにも一致しない
ので、全体が拒否され(何も実行されません)ます。つまり `&&` を使った抜け道は、どちらの
方向にもありません。複合コマンドの各部分は、単独で実行する場合と同じく、それぞれに
一致する許可エントリが必要です。

**`grep` / `sleep` / `ls` の挙動が一貫していないように見える点について**: 任意の
シェル呼び出しに対して、「安全なコマンドは無条件」という組み込みの許可はありません。
ごく一部の専用ツール(ディレクトリの一覧、ファイルの閲覧 / 書き込みなど)は、そもそも
`run_command` の呼び出しではないので、権限のゲートを完全にスキップします。単純な
ファイル / ディレクトリ操作が普通に動くのはそのためです。しかし、agy が `run_command`
を通じて実際のシェルコマンドとして何かを実行しようとした時点で、そのコマンドがどれだけ
無害でも、一致する `permissions.allow` のエントリが必要です(確認済み: 単なる `grep` や
`ls` でも、この方法で呼ぶと、エントリが 1 つも設定されていなければ `rm` とまったく
同じく拒否されます)。これは許可リストを狭めても悪化するものではなく、エントリを追加
したことで起きる新しい挙動でもありません。ヘッドレスの `--mode accept-edits` は、
もともと `run_command` の呼び出しすべてに明示的な一致を求めており、例外はありません。

## Managing permissions from Slack(Slack からの許可の管理)

Slack を離れずにプロジェクトの許可リストを操作する方法は 2 つあります。

- **拒否の返信に付くボタン**: 許可して再実行 をクリックすると、そのエントリを *この会話に
  限って* 許可し、*まったく同じプロンプト* を *まったく同じ会話* に対してすぐに再実行
  します。「許可を追加したので、自分でもう一度試してください」で終わらず、実際の結果が
  見られます。ワンクリックで恒久的に許可する手段は、意図的にありません。恒久的に
  許可したい場合は、下の `/agy-permissions add` を使ってください。`run_command` だけで
  なく、拒否メッセージ自身が許可すべきエントリを正確に示しているものであれば、どの
  拒否にもボタンが付きます(`read_url_content` で確認済み。たとえば
  `read_url(support.yayoi-kk.co.jp)`。この許可は URL ごとではなくドメインごとである
  点に注意してください。agy 自身がその粒度を使っているためです)。
  - 1 回のターンで **2 つ以上の異なる拒否が同時に** 起きた場合、それぞれに独自のボタンの
    組が付くうえに、すべてをまとめて 1 クリックで許可するボタンの組がもう 1 つ現れます。
    個別のものを 1 つずつクリックすると、1 つだけ許可してすぐに再試行するため、残りに
    再び当たる可能性が高いからです。
  - 許可は、その再試行が終わった瞬間に取り消されるわけでは **ありません**。下の
    「Temporary grant lifetime」を参照してください。
  - 2 つ目のボタン 拒否 も常に付きます。何も許可せず、メッセージを更新してその旨を
    伝え、次にどうするかをスレッドで返信するよう促します。agy には何も送り **ません**。
    拒否のメッセージで、agy はすでに知っていることをすべて把握しているので、新しく
    報告することがありません。また、自力で「別の方法を探して」と促すと、あなたが
    たった今断ったことを迂回するよう仕向けてしまうからです。
- **`/agy-permissions` スラッシュコマンド**(ブリッジ対象のチャンネルのみ):
  - `/agy-permissions list` — 現在のエントリをすべて、番号付きのプレーンテキストで表示
    します(エントリごとのボタンはありません。そのほうが単純で、以前のバージョンの
    ように Slack のブロックごとの長さ・数の制限に左右されません)。
  - `/agy-permissions add <command>` — 恒久的に追加します。素のコマンド(`kind(...)` の
    ラッパーを入力していないもの)は、以前と同じく `command(<その内容>)` で包まれます。
    `read_url(example.com)` のような完全なエントリを入力した場合は、そのまま使われます。
  - `/agy-permissions remove <command>` — 同じ規則で削除します。`list` の番号を 1 つ以上
    (スペースまたはカンマ区切り。たとえば `/agy-permissions remove 1 3 5`)指定する
    こともでき、長いコマンド文字列を打ち直さずに、複数をまとめて削除できます。
  - `/agy-permissions stats [days]` — 直近 N 日間(既定 30)に最も多く求められた
    エントリ(引数を含む)と、それぞれが要求された回数 / 1 回だけ許可された回数 /
    恒久的に許可された回数 / 拒否された回数。すべての要求と結果はブリッジの state db に
    記録されるので、何度も「1 回だけ」許可しているエントリを、根拠をもって恒久的な許可に
    昇格できます。

どちらの方法も、書き込み先は **そのチャンネル自身のプロジェクト** の
`~/.gemini/config/projects/<project-id>.json`(`permissionGrants.allow`)で、ファイル内の
ほかの内容はそのまま保たれます。agy のグローバルな
`~/.gemini/antigravity-cli/settings.json` には決して書き込みません。あるチャンネルで
承認された許可が、別のプロジェクトの会話で使われることはありません。追加 / 削除は
すべてログに記録されます。

### エージェントを持ち場に留める(Keeping the agent inside its lane)

エージェントはあなたの OS ユーザーとして動くので、以下はいずれも厳密なセキュリティ上の
境界ではありません。ただし、ありがちなミス(と手軽な探りを入れる行為)を、はっきりと
失敗させます。

- **`settings.json` の `permissions.deny`**(deny は allow に優先し、読み取りの deny は
  書き込みの deny を含意します): ブリッジ自身のインストール先ディレクトリ、その
  設定 / state ディレクトリ(Slack のトークンがあります)、agy 自身の
  `settings.json` / `config` を列挙します。たとえば `read_file(<prefix>)`、
  `read_file(~/.config/agy-slack-bridge)` です。`tools/install.py` が、これら(と対応する
  `write_file` の deny)を書き込みます。これらは重要です。`accept-edits` はそれ自体では
  ワークスペース外への書き込みを拒否しません(実機の agy で確認済み)。そのため
  deny ルールが防壁になります。
  これが対象とするのは agy 組み込みのファイルツールだけです。シェルの `cat` は *コマンド*
  なので、通常どおり許可のフローを通ります。ブリッジは、deny ルールによるブロックを
  最終的なものとして扱います。許可のボタンは出さず、代わりに「deny ルールによって
  ブロックされた」という注記を出します。
  あわせて、`trustedWorkspaces` も実際のプロジェクトのディレクトリだけに絞っておく
  ことをお勧めします。
- **各プロジェクトの許可リストは短く保ってください。** 許可ルールは前方一致です。
  `echo` は `echo x > file` も許可し、`cat` / `grep` / `tail` は何でも読め、`agy` は
  `agy --dangerously-skip-permissions ...` を許可します。
- **許可ボタンの抑制**: 1 つの会話で 10 分以内に権限ボタンのプロンプトが 3 回を超える
  と、ボタンの提示をやめます(その旨も表示します)。これにより、エージェントが、
  どれかがクリックされることを期待して、安上がりにプロンプトを繰り返し出させることが
  できなくなります。その会話であなた自身が何かを許可すると、カウントはリセットされます
  (見守っているのが明らかだからです)。そのため、正当な試行錯誤のセッションが打ち切られる
  ことはありません。
- **各プロジェクトの共通ルールファイル**(`.agents/rules/agent-safety-rules.md`。
  `tools/setup_agy_project.py` がリンクします): ブリッジや agy の内部を調べないこと、
  キャンセルされた / 拒否されたツールは回避せずそのまま報告すること、ルールファイル
  自体を削除したり無効にしたりしないことを、エージェントに伝えます。
- **サイレントな拒否**: agy は、拒否された `run_command` のステップを、エラーも出力も
  なしに DONE として終えることがあります(stderr には「auto-denied」と表示されます)。ブリッジ
  はステップ自体からコマンドを復元し、通常の許可ボタンを提示します。このようなステップは、
  空応答の自動再試行における「進捗」にも数えません。ブリッジが他の方法では把握できない
  拒否を agy が報告した場合は、`DIAG` 行がログに出力されます。

### Slack からのモデル切り替え(Switching models from Slack)

`config.yaml` のチャンネルの `model` / `effort`(上記参照)は、あくまで既定値です。
`/agy-model`(ブリッジ対象のチャンネルのみ)を使うと、`config.yaml` を編集したり
ブリッジを再起動したりせずに、実行時にチャンネルごとに上書きできます。

- `/agy-model` または `/agy-model list` — チャンネルの現在のモデル / effort(上書き、
  または config の既定値)と、選択肢の全一覧(`agy models` から取得し、5 分間キャッシュ)
  を表示します。
- `/agy-model set <model id> [low|medium|high|max]` — 次のメッセージから、そのチャンネルを
  切り替えます。モデル ID が `agy models` に載っていないものは拒否されます。モデル ID の
  中には、`-high` / `-low` などのサフィックスで推論の段階をすでに含んでいるものがあり、
  両方を設定すると `effort` と競合します。その場合は `effort` を付けないでください。
- `/agy-model clear` — 上書きを外し、`config.yaml` の既定値に戻します。

上書きはチャンネルごとにブリッジ自身の state db に保存され(再起動後も残ります)、
`config.yaml` 自体には一切触れません。

### agy のスラッシュコマンドの引き渡し(Passing agy slash commands through)

`/agy <command> [args]`(ブリッジ対象のチャンネルのみ)は、agy 自身のスラッシュコマンドを
そのまま `agy` に渡します。このため、コマンドごとに専用の Slack コマンドを用意する必要は
ありません。`/agy` だけを入力すると、使えるものが一覧されます。

- agy の組み込みコマンド(`/agy usage`、`credits`、`skills`、`permissions`、`config`、
  `changelog` など。一覧は agy 自身の `/help` から読み取ります)は即座に応答され、あなたにだけ
  見えます。
- それ以外(`/agy plan <task>` や `/agy boost <task>` などのスキルコマンド)は、@メンション
  のあとに同じテキストを入力した場合と同様に、新しいスレッドで通常のエージェントの
  ターンとして実行されます(チャンネルのモデル、権限ボタン、スレッドの継続も同じです)。
- agy が対話的にしか提供しないコマンド(例: `/context`)は、agy 自身の「not available in
  print mode」エラーが返ります。モデルの変更は引き渡されません。`/agy-model` を使って
  ください。

これらのうちどれかをよく使うとわかったら、代わりに(`/agy-model` のように)専用の
Slack コマンドを用意してください。

`/agy-link [conversation id]` は、チャンネルで最後に動いた会話を antigravity.google.com の
Web UI で開くリンクを(あなたにだけ)返信します(Slack はスレッドの中からスラッシュ
コマンドを送れないため、「現在」は「このチャンネルの最新」を意味します。別の会話を選ぶ
には会話 ID を指定します)。`agy remote-control` デーモンが登録され、同じ Google アカウント
でサインインしている必要があります。URL の `<instance>` は、CLI のインストール uuid +
`-v2` です(`~/.gemini/antigravity-cli/antigravity_state.pbtxt` から読み取ります。
`agy remote-control status` が表示するわかりやすい名前では **ありません**)。上書きするには
`AGY_REMOTE_INSTANCE` を設定します。

特定のスレッドのリンクを取得するには、**メッセージショートカット**を登録します
(Slack アプリ -> Interactivity & Shortcuts -> Create New Shortcut -> On messages)。
コールバック ID は `agy_open_web_ui` です。登録すると、ブリッジ対象のチャンネルの
スレッド内にあるメッセージなら、どれでも「...」メニューに表示され、そのスレッドの
会話リンクを(あなたにだけ、そのスレッド内で)返信します。Socket Mode では Request URL は
不要で、ボタンと同じ Interactivity の設定を使います。

### モデル使用量(クォータ)の確認(Checking model usage (quota))

- `/agy-usage` — モデルグループ(Gemini / Claude+GPT。それぞれ 5 時間枠と週枠)ごとの
  残りクォータを、JST でのリセット時刻とともに表示し、チャンネルの現在のモデルが
  使うグループを強調します。データは agy 自身の `/usage` から取得します(モデルの呼び出し
  がないのでクォータは消費せず、60 秒間キャッシュします)。
- **クォータ低下の警告**: 返信のあと、チャンネルのモデルグループに 10% 以下の枠が
  あれば、ブリッジはスレッドに 1 行の警告を追加し(グループごとに 1 時間に 1 回まで)、
  `/agy-model` を案内します。
- **App Home タブ**: アプリの Home タブを開くと、同じ使用量と、各チャンネルの現在の
  モデルが表示されます。有効にするには、Slack アプリ -> App Home -> 「Home Tab」を
  オンにし、Event Subscriptions -> Subscribe to bot events に `app_home_opened` を
  追加します。タブを開くと、キャッシュされた `agy /usage` を最大でも 1 分に 1 回だけ
  消費します。

**一時的な許可の存続期間(Temporary grant lifetime)**: 以前は、1 回限りの許可は、その
再試行が終わった瞬間に削除されていました。しかしこれは、異なる許可が *複数* 順番に
必要になるタスクでは、実際には誤りでした。2 つ目が許可される時点で 1 つ目はすでに
なくなっており、両方が必要な後続の再試行では 1 つ目がまた拒否されてしまうからです。
そこで現在は、`grant_once` のエントリは会話に結びついています。その会話で、新たな拒否が
**まったく** ない次のターンが来た時点(自然な「このタスクはいったん終わった」という
合図)で解放されます(そして、*同じプロジェクト内* のほかの会話が、まったく同じエントリを
使っていない場合に限り、プロジェクトの `permissionGrants.allow` から *実際に* 削除
されます)。タスクの途中で放置され、きれいな状態で戻ってこない会話のための安全策として、
バックグラウンドのスイープが `AGY_TEMP_GRANT_MAX_AGE_SEC`(既定 3600 秒)より古いものを
強制的に解放します。確認間隔は `AGY_TEMP_GRANT_SWEEP_INTERVAL_SEC`(既定 300 秒)です。
作業が終わる前にスイープが走った場合は、また新しい拒否が表示されるだけです。もう一度
ボタンをクリックしてください。害はありません。

**注意(テストで確認済み)**: agy の結果に含まれる `denied_actions` / `duration_seconds` /
`usage` は、1 回のターンに限定されず、会話全体の累積です。そのため、ボタンのない
プレーンテキストの「一部のツール実行が権限不足で拒否されました」という警告は、たった
今起きたことではなく、その会話の履歴に *古い*、未解決の拒否が残っていることを意味する
場合があります(agy は、拒否されたコマンドを再度試して失敗する代わりに、再試行しない
ことを黙って選ぶことがあります)。ボタンが表示されるのは、agy のストリームがこのターンの
*新しい* 拒否を示している場合に限ります。許可すべき正確なコマンド行があるのは、その
場合だけだからです。また、ボタンをクリックしたあとに agy へ送り返される再試行の
プロンプトは、元のメッセージをそのまま再送するのではなく、許可されたばかりのコマンドを
明示して「今すぐ実行して」と伝えます。許可が出たあとでも、agy が自力で再試行するとは
限らないからです。

これは、会話のまさに最初のターンでも起こりえます(テストで確認済み)。非同期で実行された
ツール呼び出し(`WaitMsBeforeAsync`)は、その権限チェックの解決が、この print モードの
呼び出しがすでにストリームを取り込んで戻った *あと* になることがあります。そのため、
`denied_actions` にはすでに反映されていても、報告できる新しい step_update がありません。
ブリッジが「過去のもの」と呼ぶのは `num_turns` が 1 より大きい場合だけです。ターン 1 では、
何かを「過去」にできる前のターンがないので、新しい非同期の拒否が起きた可能性が高いが、
間に合うように取得できなかった、と伝えます。

その注記を表示する前に、ブリッジはあなたの代わりに「実行して」を、最大
`GREY_QUESTION_AUTO_RETRIES`(2)回まで黙って再送します。これまでに見られたすべての
事例のログ分析では、毎回 2 回以内(たいていはすぐ次の 1 回)で解消していました。多くの
場合、本当に持続している拒否ではなく、上記の非同期のタイミングのずれにすぎないからです。
解消するまで繰り返すのではなく、意図的に回数を区切っています。本当に何かの理由で止まって
いる実行のコストと時間に上限を設けるためで、それを使い切ったときにだけ、注記(あなたの
助けを求めるもの)を表示します。これが、同じターンで本物の、対処可能な拒否と連続して
起動することはありません。新しい拒否には必ず本物の `_tool_errors` が伴い、それだけで
上記の permission_errors / other_errors の処理(ボタンを含む)に回り、自動再試行は関与
しないからです。

### Usage statistics(利用統計)

オプトインの機能で、利用状況をブリッジのローカルの state DB に記録します。既定では
オフで、どこにも送信されません。

- `permission_stats`: 1 回限り / 恒久的な権限ボタンの要求と、その結果をそれぞれ記録します。

すべての記録にチャンネルのタグが付くので、プロジェクトごとの利用状況を単独で読めます。
設定は、チャンネルごとに、またはすべてのチャンネルに対して行えます。

- `config.yaml` で、チャンネル自身の `telemetry:` ブロックの下、またはすべての
  チャンネルに対してトップレベルに書きます。チャンネル自身の設定が、トップレベルの
  設定に優先します。
- Slack からは、`/agy-stats on|off <feature>` で、このチャンネルだけを変更します。
  `all` を付けるとすべての場所に設定します(トップレベルの既定値と、設定済みの全
  チャンネルそれぞれの設定)。どちらの場合も、変更は `config.yaml` に書き戻され、
  すぐに有効になります。

統計はこのチャンネルのみを表示します。

- `/agy-stats` — このチャンネルの現在のオン / オフの状態と、その設定の出どころ。
- `/agy-stats buttons [days]` — エントリごとの、権限の要求、1 回限りの許可、恒久的な許可、
  拒否。このチャンネルのみ。
- `/agy-permissions stats [days]` — 同じ権限の件数で、「恒久的な許可を追加する」判断の
  ためのものです。このチャンネルのみ。

機能をオフにすると、新しい記録が止まります。既存の記録は DB に残ります。

### Mermaid diagrams(Mermaid の図)

agy の応答にある ` ```mermaid ` のフェンスブロックは、PNG に描画されてスレッドにファイル
としてアップロードされます。生の図の構文(Slack には描画する手段がありません)として
投稿されることはありません。これにはオプションの `playwright` パッケージと Chromium の
インストールが必要です。

```
.venv/bin/pip install playwright
.venv/bin/python -m playwright install chromium
```

マシンに、別のプロジェクト用の Playwright の Chromium(たとえば
`~/.cache/ms-playwright` の下)がすでにキャッシュされている場合、同じバージョンの
`playwright` をここにインストールすると、2 つ目をダウンロードする代わりにそのキャッシュを
再利用します。

- 描画は、ヘッドレスの Chromium の中で
  `mermaid.render()`(公式の JS API。CDN から一度だけ取得し、
  `~/.cache/agy-slack-bridge/mermaid.min.js` または `$AGY_BRIDGE_CACHE_DIR/mermaid.min.js`
  にキャッシュされます。キャッシュ先を変えるにはその環境変数を設定します)で行います。
  図のソースを HTML として解釈することは決してないので、`<`、`>`、`&` や意図的な
  `<br/>` を含むラベルも、ページを壊さずに正しく出力されます。
- `playwright` がインストールされていない場合や、特定の図の描画に失敗した場合(構文の
  誤り、描画のタイムアウトなど)、そのブロックは黙って消えるのではなく、プレーン
  テキストのまま残されます。何も失われず、描画されないだけです。
- 描画された PNG は、その会話自身の
  `~/.gemini/antigravity-cli/brain/<id>/scratch/mermaid/` の下に書き込まれ、自動では
  削除されません。小さなものですが、図をよく使う場合は、ときどき `find` で確認すると
  よいでしょう。

### Config drift detection(設定ドリフトの検出)

agy プロジェクトが依存するファイルの中には、意図的にどこにも公開 **されていない** ものが
あります。このマシンに実際にインストールされているもの、プロジェクトが外部 API に
どう認証するか、その他のローカルで運用している設定などです。再取得して差分を取れる
正規のコピーがないので、代わりにブリッジは、人間が最後に明示的に正しいと確定した内容を
追跡します。

チャンネルに `watched_config_files`(その agy プロジェクト自身のワークスペースのルートからの
相対パス。`config.example.yaml` を参照)を設定すると、そのチャンネルで有効になります。
バックグラウンドのチェック(起動時に 1 回、その後 `AGY_CONFIG_DRIFT_CHECK_INTERVAL_SEC`
秒ごと、既定 1800)が、監視対象の各ファイルのハッシュを取り、最後に確定したベースライン
と比較します。

- **まだ一度も確定されていない**: ボタン 1 つ付きでチャンネルに投稿します。
  **この内容を正として確定** をクリックすると、現在の内容を信頼できるベースライン
  (ハッシュとバックアップコピー。どちらもブリッジが保持)として受け入れます。
- **前回の確定以降に変更された**: ボタン 2 つ付きの警告を投稿します。同じ
  **この内容を正として確定**(意図した編集で、新しいベースラインとして受け入れる)と、
  **確定済みの内容に戻す**(最後に確定したバックアップからファイルを復元する。たとえば
  あなたが頼んでいないのにエージェントが変更した場合)です。
- **変更なし**: 何もしません。未解決の状態は、チェック間隔ごとに再投稿されません。
  *さらに* 変更があった場合(新しいハッシュ)にだけ、再び通知します。

バックアップとベースラインは、`AGY_CONFIG_BACKUP_DIR`(既定
`~/.config/agy-slack-bridge/config-backups/`)とブリッジ自身の state db の下にあり、
監視対象のプロジェクト自身の git 履歴にはありません。
