# tools/ — インストールして使うツール群

Slack ブリッジ経由で動かす agy プロジェクトに共通の、安全規則・フック・Drive CLI と、
それらをプロジェクトに設定するスクリプトです。**このリポジトリのチェックアウトから直接
使うのではなく、`install.py` で固定のインストール先に入れて使います**(理由は下記)。

| ファイル | 内容 |
|---|---|
| `install.py` | ブリッジ本体・`tools/`・venv をインストール先に入れる。設定ディレクトリのひな形も作る |
| `setup_agy_project.py` | agy プロジェクトの設定(対話式、冪等)。インストール先から実行する |
| `agy_settings.py` | agy の machine-wide な `settings.json` の読み書き(deny / trustedWorkspaces のみ)。install と setup が共有 |
| `bridge_config.py` | `config.yaml` / `env` を、コメントを残したまま書き換える部品 |
| `agent-safety-rules.md` | エージェント向けの行動規則(ブリッジ内部を調べない、拒否を迂回しない、など) |
| `hooks.json`, `hooks/script_integrity.py` | `run_command` の PreToolUse フック。恒久許可したスクリプトが、承認後にこっそり書き換えられていないかを検査する |
| `gdrive_cli.py` | Google Drive 用の、固定・限定コマンドの CLI。`--profile` で認証情報と制限を切り替える。[`gdrive-profile.md`](gdrive-profile.md) |

## なぜインストールするのか

権限モデルを支える部品(Drive CLI、フック、ポリシー、ブリッジ本体)が、エージェントの
書き込める場所(プロジェクトの中、git のチェックアウト)にあると、エージェントがそれらを
書き換えられてしまいます。そこで次のようにします。

- インストール先(既定 `~/.local/share/agy-slack-bridge`)と設定ディレクトリ
  (既定 `~/.config/agy-slack-bridge`)を、`install.py` が agy の
  `permissions.deny`(読み取り・書き込み)の対象にする。
- Drive CLI とフックは、プロジェクトにコピーせず、インストール先のものを絶対パスで直接使う。
  プロジェクト内にスクリプトが無いので、プロジェクトごとの封印(seal)は要らない。
- ポリシー(許可フォルダ、アップロードの制限など)は、設定ディレクトリのプロファイルに置く。
- 恒久許可の seal(ブリッジが書く)とフックの実行履歴も、プロジェクトの中ではなく設定ディレクトリの
  `integrity/<プロジェクトのキー>/` に置く。

エージェントは同じ OS ユーザーで動くので、ユーザー所有のインストール先は deny ルールで
守るだけです。agy の `accept-edits` は、ワークスペース外への書き込みを既定では拒否しない
ことを実機で確認済みで、この `deny` が実質的に唯一の防壁です。最も堅くしたいときは、`--prefix /opt/agy-slack-bridge` のように root で
インストールします。

## 使い方

```sh
# 1. インストール(チェックアウトから。通常ユーザーで)
python3 tools/install.py [--prefix DIR] [--config-dir DIR] [--with-gdrive]

#    root で /opt に入れる場合
sudo python3 tools/install.py --prefix /opt/agy-slack-bridge [--with-gdrive]
python3 /opt/agy-slack-bridge/tools/install.py --prefix /opt/agy-slack-bridge --config-only
#    (--config-only はコードに触れず、通常ユーザーとして設定ディレクトリと settings.json だけ設定する)

# 2. プロジェクトの設定(端末から、人間が実行。インストール先のものを使う)
<prefix>/.venv/bin/python <prefix>/tools/setup_agy_project.py [<プロジェクトのパス>] \
    [--prefix <インストール先>] [--bridge-config-dir <設定ディレクトリ>]
```

`install.py` は最後に、続けて `setup_agy_project.py` を実行するか確認します(Y でそのまま実行、
N なら後で実行するコマンドを表示)。`--no-setup` で確認を省略できます。
`install.py` を再実行するとコードが入れ替わります(アップグレード)。インストール先に
自分で置いたファイルは消えます。設定ディレクトリの既存ファイルは上書きしません。
インストールしたファイルは 0444 です(事故防止であって防御ではありません)。チェックアウト自身を `--prefix` にはできません。

`setup_agy_project.py` は対話式のメニューです。最初にプロジェクトの一覧（と、新規作成・Slack トークン・終了）が出て、
プロジェクトを選ぶと、そのプロジェクトのメニュー（全部設定、ルールとフック、Slack チャンネル、Drive CLI、状態）が出ます。
`--all` を付けるとメニューを出さず全部を順に実行します。パスの質問はタブで補完できます。「全部設定」では、何度実行しても安全で、現在の値が既定値として表示されるので、
変更や修復も同じコマンドです(Enter: そのまま、`-`: 値を消す)。順に次を行います。

0. 対象の指定: パスを省略すると、agy に登録済みのプロジェクトの一覧から番号で選ぶか、
   新しいディレクトリのパスを入力する(既存のディレクトリを指定したときだけ上書きの確認がある。既存のプロジェクトは、そのディレクトリを使う。
   ディレクトリの無いプロジェクトは、Drive の許可とチャンネルの対応づけだけ行う)。
1. ディレクトリの用意(無ければ作成)。git 管理は必須なので、git リポジトリでなければ `git init` する。
2. agy への登録(`agy --new-project -p hi` を、そのディレクトリで実行する。プロジェクト名は
   ディレクトリ名になる。モデルを 1 回呼ぶ)。
3. `~/.gemini/antigravity-cli/settings.json` の `trustedWorkspaces` に対象を追加し、安全規則の
   リンク(`.agents/rules/agent-safety-rules.md`)への書き込みの `deny` を足す
   (`.agents/rules/` の他のルールや `AGENTS.md` は編集できるまま)。`allow` はここには書かない。(インストール先・設定ディレクトリを守る machine-wide の
   `deny` と、グローバルの `hooks.json` へのフック登録は `install.py` が行う。)
   併せて、フックの状態ディレクトリ(`<設定ディレクトリ>/integrity/…`)を作る。
   以前のセットアップが置いたプロジェクトごとの `.agents/hooks.json` のフックは外す
   (グローバルのフックと二重に動くため)。
4. 対象の `.agents/rules/` に、安全規則へのシンボリックリンクを置く(`AGENTS.md` は触らない。
   エージェントが自由に編集してよい)。以前のセットアップが作った `.agents/` 直下のリンクと
   `AGENTS.md` の読み込み行は取り除く。`.gitignore` に `scratch/` を追記
   (scratch について何も書かれていない場合のみ)。
5. Slack チャンネルの対応づけ(`config.yaml` の `channels`。必須はチャンネル ID だけで、その後に「任意の項目を設定するか」を聞く):
   表示名、アイコン、モデル(`agy models` の一覧から選ぶ。起動時に裏で取得し、ブリッジの `/agy-model` と `<設定ディレクトリ>/models-cache.json` を共有(1時間))、effort、監視する設定ファイル、権限ボタンの統計、スクリプトの要約の表示（`script_summary`）。
   書き換えは該当エントリだけで、他のコメントや項目は残る(元のファイルは `config.yaml.bak`)。
6. 未設定なら `env` の Slack トークン。
7. (任意。必須の設定のあと)Drive CLI を使うか聞き(「順に全部」のときだけ)、使うなら、プロファイル名(agy のプロジェクト ID から自動で決まり、重ならない。
   他のプロジェクトのプロファイルがあれば、新規作成か、そのプロジェクトと同じ設定・権限の共有かを選ぶ)で、プロファイル(`<設定ディレクトリ>/gdrive/NAME.json`、[`gdrive-profile.md`](gdrive-profile.md))を
   対話で作成・設定する。
   設定すると、エージェント向けの使い方 `.agents/rules/gdrive-cli.md` も書く（許可リストと同じ絶対パスのコマンド、プロファイルで有効なコマンドだけ。
   プロファイルの切り替え・方針の変更で作り直し、Drive 設定を外すと削除する。このスクリプトが作ったものでないファイルが既にあれば、置き換えるかを聞く（既定 N））。
   - 無ければ、認証の種類(`service_account`(推奨。Drive のフォルダをそのメールアドレスに共有するだけ)/ `oauth`)と資格情報を取り出すコマンド(と、
     必要ならスコープ)を聞いて作る。既存のプロファイルの資格情報とスコープには触らない。
   - 方針(有効なコマンド、許可フォルダ(フォルダの URL か ID)、アップロードの拒否パターン
     (今のまま / 既定に追加 / 置き換え))は、現在値(新規なら既定値)を見せて、変えるかを聞く。
     既定値と違う項目だけをファイルに書く。権限が広がる変更(コマンドの追加、フォルダ制限の解除、
     拒否パターンを外す)は、差分を見せたうえで別に確認する(既定は no)。
   - 有効な読み取り系サブコマンド(`list`/`search`/`meta`/`read`/`download`)を、そのプロジェクト
     自身の `permissionGrants.allow` にだけ追加する。無効にしたコマンドの、以前の許可は外す。
     書き込み系は許可に入れず、毎回の承認。
   - プロファイルは 0600、置き場は 0700 で書く(壊れているプロファイルは上書きしない)。
   - 設定済みのプロジェクトで Drive を選ぶと更新メニューが開く: 方針の変更 / 認証情報の入れ直し
     (方針は残す。使わなくなった保存済みの鍵は削除) / 別のプロファイルへの切り替え(専用に戻す・
     他のプロジェクトと共有) / このプロジェクトの Drive 設定を外す。外す・切り替えで他のどのプロジェクトも
     使わなくなったプロファイルは、確認のうえ削除できる(既定は残す)。

設定を変えたあとは、ブリッジの再起動が必要な場合があります。

### マシン固有のファイル(任意)

`<設定ディレクトリ>/shared/` に次のファイルがあれば、プロジェクトの `.agents/rules/` に**コピー**します
(リンクにしないのは、設定ディレクトリをエージェントの `read_file` が `deny` で拒否していて、リンク先だと
エージェント自身が読めないため。`deny` は `allow` より優先で、一部だけ除外もできません。元を直したら、
再実行すると反映されます。コピーと違う内容になっている場合は、上書きするかを聞きます)。
マシンごと・運用者ごとの内容なので、このリポジトリには含みません。

- `local-tools.md` — このマシンで使えるツールの一覧

`.agents/rules/` のルールファイルには、先頭に frontmatter(`---` / `trigger: always_on` / `---`)が
必要です。無いと、エラーにならずに無視されます(実機で確認済み)。付けていないと
`setup_agy_project.py` が警告します。
`.agents/rules/` のルール(通常のファイル、シンボリックリンクとも)と、ファイル単位の
`write_file` の deny は、実機で動作を確認済みです。シェル(`rm` / `mv` など)による削除・移動は
deny の対象外で、通常の許可フローと、安全規則 9 で防ぎます。

## 許可の範囲について

ブリッジ自身は、どのプロジェクトにも共通で効く許可を作りません(`docs/permissions.md` 参照)。
このスクリプトも同じ方針で、`settings.json` に書くのは `deny` と `trustedWorkspaces`
(絶対パス指定で、プロジェクトを問わず共有して安全なもの)だけです。
`allow` は、対象プロジェクト自身の `permissionGrants` にしか書きません。

`--profile` は許可エントリの一部になります
(`command(<prefix>/.venv/bin/python -I <prefix>/tools/gdrive_cli.py --profile <名前> list)`)。
プロジェクトごとに別のプロファイル名を使えば、あるプロジェクトの Drive 許可が、別プロジェクトの
認証情報を使う権限にはなりません。名前の先(保管先、スコープ、許可フォルダなど)はプロファイルの
中にあるので、後から変えても承認済みのコマンド文字列は変わらず、再承認は要りません。
プロファイルの書き方は [`gdrive-profile.md`](gdrive-profile.md)。

### Drive CLI を使うときの前提

- インストール時に `--with-gdrive` を付けて、Google 系パッケージをインストール先の venv に入れる。
- 資格情報を取り出すコマンド(`aws`、`op` など)が、ブリッジを動かすユーザーで実行できること。
- サービスアカウントの場合は、そのメールアドレスに対象フォルダを共有しておく。
- 削除・移動・共有設定の変更はコマンド自体がありません。

## フックについて

フックは、`install.py` が agy の **グローバルな `~/.gemini/config/hooks.json`** に一つだけ登録します
(`command` は、インストール先のフックの絶対パスに `--config-dir` を付けたもの。同じファイルの
他のフックは残します)。プロジェクトごとの `.agents/hooks.json` は使いません。`~/.gemini/config/`
は deny の対象なので、エージェントは書き換えられません。

フックが守るのは、`/agy-permissions add` で恒久許可した **プロジェクト内の** スクリプトです
(封印したハッシュと違えば拒否、git commit 必須)。封印(`permanent.json`)も、それ以外の
スクリプトの実行履歴(`hashes.json`)も、設定ディレクトリの
`integrity/<プロジェクトのキー>/` に置きます。キーはプロジェクトのルートの実パスのハッシュで、
`setup_agy_project.py` が、このディレクトリを作ったプロジェクトだけをフックの対象にします
(作っていないプロジェクトでは、フックは何もしません。グローバルなので、ユーザー自身の
対話的な agy の利用にも発火しますが、何もせずに素通りします)。インストール先のツールは
プロジェクトの外にあるので、封印の対象ではありません。

プロジェクトごとの `.agents/hooks.json` に `script-integrity` を残すと、フックが二重に動き、
先に実行履歴が更新されて検知が効かなくなります。`setup_agy_project.py` は、以前の
セットアップが置いたものを見つけたら外します。

## 共有ファイルを足したとき

`tools/` に置いたものは、`install.py` が丸ごと同期します。プロジェクトの `.agents/` に
リンクして `AGENTS.md` に読ませたいものは、`setup_agy_project.py` の
`AGENTS_MD_INCLUDES` と、リンクする処理に追記してください。
